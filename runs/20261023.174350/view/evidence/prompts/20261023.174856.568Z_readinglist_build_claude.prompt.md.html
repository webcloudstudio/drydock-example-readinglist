# COMPASS: ReadingList

## Compass
A web application that lets a reader keep a personal list of books to read. The reader adds a book with a title and author, views books in the order they were added, and removes books. It serves a single reader who needs a simple, dependable reading list with clear feedback on invalid input.

## Constraints
- The application is a web application with a user-facing interface.
- The completed application must provide a POSIX-compatible `bin/test.sh` runnable from the application root with `sh bin/test.sh`.
- `bin/test.sh` must exit zero only when every automated test passes.

- Never accept an empty title or an empty author; reject the submission with a clear error message.
- Never present books in any order other than the order they were added.
- Never report a test run as passing unless every automated test passes.
- Never omit a removed book from the next list read only partially; a removed book must not reappear.

### How do we execute and measure Acceptance Criteria in this language?

An Acceptance Criterion (AC) is an executable check of Blueprint-required behavior. Use the
existing Programmatic Acceptance format: a Python script with assertions against the built
product. Drydock executes each criterion through `languages/python/acceptance/runner.py`; `pytest -q`
runs the project test suite. Retain the criterion ID, observed values, stdout/stderr and result;
an assertion failure fails the check. The harness reports failure operands and available case
counts. Code coverage and persistence interactions require explicit instrumentation; record
available observations as key/value data associated with the criterion. Missing observations
are unknown, not proof that code or an interaction was unused.

### How does this language provide the shared persistence contract?

Use `stack/persistence.md`. Drydock copies `Rigging/languages/python/persistence/{db,sqlite,postgres}.py` and generates
`persistence/{schema,__init__,testing}.py` plus `schema.sql` from `DATABASE.md`. Call
`open_database(dsn)` and `db.<table>.<operation>(...)`; use `persistence.testing.db_session()`
for criteria. SQLite uses the standard library; PostgreSQL needs `psycopg[binary]` in the project
dependencies. Both engines ship together and the DSN selects the engine. Library verification
lives in `tests/test_shipped_database.py`; a Target still verifies its own schema and operations.

## Purpose

ReadingList is a single-reader web application. A reader adds a book with a title and author, views books in the order added, and removes books. Empty titles or authors are rejected with a clear error. The application ships automated tests and a POSIX `bin/test.sh`.

## Technology Stack

Derived from `TECHNOLOGY_STACK.md`; that file is the decision of record.

| Technology | Where it applies |
|------------|------------------|
| Python | Implementation language; project tree and environment. |
| Flask | Web framework; application factory `app_server.create_app()`. |
| SQLite | Persistence through the generated `persistence` package. |
| pytest | Automated tests, run as `pytest -q`. |
| HTML/CSS | Server-rendered pages with minimal CSS, no client-side JavaScript. |

## Project Layout

| Path | Role |
|------|------|
| `pyproject.toml`, `uv.lock` | Dependency manifest (Flask, pytest) and committed lockfile. |
| `.venv` | Environment created by `uv venv`. |
| `app_server/__init__.py` | `create_app() -> Flask`. |
| `app_server/testing.py` | `web_client()` plain callable. |
| `app_server/routes/` | Flask blueprints: JSON routes (`books.py`) and page routes (`pages.py`). |
| `app_server/services/books.py` | Book service: `add_book`, `list_books`, `remove_book`, `validate_book_input`. |
| `app_server/templates/` | Jinja templates (base layout, reading list page). |
| `persistence/` | Generated by Drydock from `DATABASE.md`; never hand-written. |
| `tests/` | pytest suite with `conftest.py` exposing the `web_client` and `db_session` fixtures. |
| `bin/test.sh` | POSIX test runner. |

## Module Ownership

| Boundary | Owning module | Allowed low-level access |
|----------|---------------|--------------------------|
| Persistence | `persistence` (generated) | The only module that touches SQLite. |
| Book rules and orchestration | `app_server.services.books` | Calls `db.books.<verb>(...)` only. |
| HTTP routes | `app_server.routes` | Call the service; never the database. |
| Configuration | `app_server.__init__` | Resolves `DATABASE_URL`, then `DATABASE_PATH`, then `data/app.db`. |
| File stores / external services | None | Not used. |

## Layering

Routes call services; services call `db.<table>.<verb>(...)`. SQL, sessions, table names, and column names never cross the persistence boundary. Books are always returned ordered by id ascending, which is the order added.

## Technical Decisions

- Test runner command is `pytest -q` from the application root.
- Rejected input returns 400; removal of an unknown book returns 404 (see `DECISIONS.json`).
- Server-rendered forms provide the user interface; JSON routes share the same services.
